# Revision And Review Convergence

## Route The Finding, Do Not Write The Fix

A finding proves a problem. It does not authorize the fix it proposes.

Decide only the **next route**:

- a factual contradiction: Scout or Researcher, if needed;
- a correction to the assignment or spec framing that stays inside existing direct authority: a fresh Assignment Engineer for a revision assignment;
- a product, authority, or trust choice that must be settled before revision: Advisor or user decision; and
- implementation freedom the spec already allows: no spec revision.

**Ben execution feedback:** read Ben's blocker and its direct evidence. A repository fact or evidence gap goes to Evidence Routing; for an implementation choice the spec already allows, tell Ben he may choose it. Do not restart master writing unless the blocker changes the roadmap or capability boundaries. After any corrected spec passes substantive review, hand the current reviewed single back to Ben.

Do not copy a Reviewer's or Ben's proposed fix into the Writer assignment. Give the Assignment Engineer the current spec, the direct authority, the exact finding, and the relevant evidence. The Engineer writes the smallest revision assignment.

Keep the Task ID, Task Name, mode, and canonical Spec Output Path the same across revision rounds.

## Convergence

Re-review the affected scope after a revision. Do not revise for polish or reopen unrelated accepted material.

If the same important issue survives two focused revision rounds, stop patching the same solution. Go back to the original actor-visible capability. Route the smallest question needed to decide whether to delete, narrow, split, or keep the disputed contract. Do not let repeated reviewer fixes pile up into a larger design.
